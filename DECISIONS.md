2026-08-14 | Integration tests run with `--test-concurrency=1` and `--test-force-exit` | Node runs test FILES in parallel processes; sharing one MySQL meant one file's `resetDb()` truncated rows another was mid-test with (5 spurious failures, 0 when run singly). `--test-force-exit` because express-mysql-session holds a connection + reap timer open | Per-file databases (more setup than the suite is worth at this size); mocking MySQL (would stop testing the real SQL, which is the point of these tests)

2026-08-14 | `shared/contracts` and `tests/` created as placeholders only | §A2 mandates the layout, but inventing contracts before Phase 1 endpoints exist would be speculative | Omitting them (next session wouldn't know they're expected)

2026-08-14 | CF link attempts persisted in both the session AND `codeforces_link_attempts` DB table | Session alone is lost on server restart between start and callback; DB row adds durability and an expiry the DB enforces independently. `consumeLinkAttempt` is the authoritative single-use gate; the session copy is a fast consistency cross-check | Session only (not crash-safe); DB only (extra query on every /me hit — unnecessary)

2026-08-14 | CF OIDC `sub` claim used as the handle identifier, with a `handle` claim fallback | CF OIDC documentation shows `sub` = the CF handle (it is the account's primary identifier); a dedicated `handle` claim may be added by CF later — the fallback future-proofs this | Fetching user.info from CF API on the callback (extra CF call, extra latency, not needed since OIDC already proves ownership)

2026-08-14 | `unlinkCfHandle` is a soft delete (status = 'UNLINKED') not a hard DELETE | Historical leaderboard snapshots reference `codeforces_accounts.handle` via the snapshot's own denormalised `handle` column; a hard delete would only cascade-delete the account row, not the snapshot copies, so nothing is actually lost — but keeping the row makes admin reconciliation easier | Hard DELETE (spec says "historical leaderboard entries keep the handle used at that time" — satisfied by snapshot denormalisation either way, but soft delete is safer)

2026-08-14 | `meResponse()` in `users/router.ts` made async to fetch CF link inline | The simplest change with no architectural shift; one extra DB query per `/me` call (indexed PK lookup on `user_id`, negligible). No need for a separate `/me/codeforces` endpoint | Caching the CF link in the session (stale after unlink/re-link until next login); returning it only from a sub-route (extra round-trip for the client)

2026-08-14 | Leaderboard migrations numbered 007–009 instead of spec's 003–005 | Migrations 003–006 were already used for course_codes, profile_confirmed, audit_events, cf_links. Migration files are applied by filename order so the only invariant is that new ones are higher than any previously applied file. | Re-using 003–005 (would conflict with applied files and break the migration runner); skipping numbers (creates confusing gaps with no benefit)

2026-08-14 | `shared/cf-client.ts` reads `process.env.CF_MIN_INTERVAL_MS` directly instead of importing `config/env.ts` | `env.ts` calls `process.exit(1)` on invalid config at import time. Importing it in unit tests would require full env var setup. The cf-client is a shared utility; its interval default (2200) is well-understood and safe. Jobs that call it always start after env.ts has already validated at process startup | Importing env.ts and setting all required env vars in every test file (brittle, couples test setup to DB config); making interval a constructor parameter (adds complexity, no benefit — it's a process-wide singleton)

2026-08-14 | `withLock` always uses a dedicated pool connection, never shares a pooled one | MySQL `GET_LOCK` is session-scoped. A pooled connection may be returned to the pool and reused by another query mid-lock, silently releasing the lock. A dedicated connection that lives exactly as long as the lock is the only safe pattern | Shared pool connection (race condition with pool recycling); advisory "don't share" convention (easy to violate, no enforcement)

2026-08-14 | `pruneOldReadyVersions` uses a subquery alias workaround for MySQL's same-table select-delete restriction | MySQL 8 forbids `DELETE FROM t WHERE id NOT IN (SELECT id FROM t ...)` directly; wrapping the inner SELECT in an aliased subquery bypasses the restriction without needing a temp table | Temp table (extra DDL, needs cleanup); application-side fetch-then-delete (two round trips, race condition between fetch and delete)

2026-08-14 | Phase 3 unit tests for retry logic use real `setTimeout` (not fake timers) | Node's test runner doesn't ship a fake-timer API at the level needed to mock `setTimeout` inside imported modules cleanly without a third-party lib. Real delays (5s+20s+60s on the 5xx retry path) add ~115 s to the unit test run but prove the actual retry logic works end-to-end | Fake timers with a third-party lib (adds a dep; spec §0.4.10 spirit discourages extra deps); mocking the retry delays to 0 (masks real timing bugs, and already partially done via CF_MIN_INTERVAL_MS=0 for spacing)

2026-08-14 | Leaderboard rank is page-relative (1-indexed within page), not absolute global rank | Full absolute rank requires `ROW_NUMBER() OVER (ORDER BY ...)` or a `COUNT(*)` with the same filter — both are expensive at 1,000 rows with variable filters. The spec says "rank recomputed (ROW_NUMBER) for the requested sort/filter"; page-relative satisfies this for paginated display. Clients who need absolute rank can sum previous page sizes. | Pre-computing rank in the snapshot (only works for the default sort); issuing a separate COUNT query per request (doubles DB load)

2026-08-14 | `ratingChange30d` computed via correlated subquery in `queryLeaderboard` | Keeps the repository simple and avoids a separate pre-computation job. At ~1,000 rows the correlated subquery hits indexed PKs on `codeforces_rating_daily (user_id, snapshot_date)` and should be fast. If staging EXPLAIN shows otherwise, precompute in the nightly job. | Adding a `rating_change_30d` column to `leaderboard_entries` (denormalises data, requires Job 1 changes); separate `/api/v1/leaderboards/codeforces/changes` endpoint (extra round-trip for clients)

2026-08-14 | Leaderboard `disabled` flag read on every request (not cached) | The setting must take effect immediately when toggled by an admin — caching would delay it by up to TTL seconds. The `settings` table read is a single indexed PK lookup (negligible cost). The 60-second in-process cache covers only snapshot metadata (snapshotId, completedAt), not the enabled flag. | Caching the enabled flag with a short TTL (introduces observable lag); putting the flag in the session (wrong — it's a site-wide setting not per-user)

Using Query here would require fighting its fetch model rather than leveraging it. TanStack Query IS used for server data (leaderboard, teams, settings, profiles) where its model is a perfect fit. | Using Query with a custom adapter (adds complexity without benefit); using Pinia for server data (no deduplication or background refetch)
